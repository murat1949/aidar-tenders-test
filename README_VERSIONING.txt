AIDAR TENDERS / PROCUREVISION KZ
ПОРЯДОК ВЕРСИЙ, КОНТРОЛЬНЫХ ТОЧЕК И ВОССТАНОВЛЕНИЯ

Дата фиксации: 03.09.2026

1. ЗАЧЕМ ЭТО НУЖНО
Проект развивается последовательными тестовыми версиями.
Чтобы через неделю, месяц или позже быстро понять:
- какая версия была стабильной;
- какие файлы ей соответствуют;
- где искать документацию;
- как восстановить работу;
используется единый порядок версий и контрольных точек.

2. ГЛАВНЫЙ ПРИНЦИП
История разработки сохраняется в GitHub через:
- ветки;
- commits;
- файлы документации.

Старые рабочие версии не нужно бесконечно держать рядом
с актуальными файлами в корне проекта.
GitHub уже хранит их историю.

3. СТАБИЛЬНЫЕ КОНТРОЛЬНЫЕ ТОЧКИ
Каждая полностью проверенная версия получает отдельную стабильную ветку.

Пример:
- test10g-stable — предыдущая стабильная точка;
- test10j-stable — стабильная точка после успешного TEST10J;
- следующие версии создаются уже от последней стабильной точки.

4. ТЕКУЩАЯ КОНТРОЛЬНАЯ ТОЧКА
TEST10J Stable.

Проверено:
- Samruk → TEST10J → Supabase → портал;
- поиск "Бумага";
- 11 лотов;
- with_techspec: 11;
- without_techspec: 0;
- лоты 4524061 и 4524060 обработаны через techspec_from_lot_card.

6. ЧТО ДЕЛАТЬ ПЕРЕД НОВОЙ РАЗРАБОТКОЙ
Перед началом TEST10K:
1) создать ветку test10j-stable;
2) убедиться, что TEST10J полностью сохранён;
3) новые изменения делать уже в новой рабочей ветке;
4) стабильную ветку TEST10J больше не менять.

7. КАК НАЗЫВАТЬ COMMITS
Рекомендуемый формат:

TEST10J Stable - <краткое описание>
TEST10K - <что изменено>
TEST10K Fix - <что исправлено>
TEST10K Stable - <что зафиксировано>

Примеры:
TEST10J Stable - Samruk lot card fallback
TEST10J Stable - documentation
TEST10J Stable - recovery instructions

8. ГДЕ ИСКАТЬ СТАРУЮ ВЕРСИЮ
Если нужно восстановить старое состояние:
1) открыть GitHub;
2) выбрать нужную стабильную ветку;
3) открыть список commits;
4) выбрать commit нужной даты;
5) посмотреть или скачать файлы именно из этого состояния.

9. ЧТО МОЖНО УБИРАТЬ ИЗ КОРНЯ
После фиксации стабильной точки старые тестовые Python/BAT-файлы
можно переносить в архив или удалять из текущей рабочей ветки,
если они уже сохранены в истории GitHub.

Это не удаляет историю GitHub.

10. ДОКУМЕНТАЦИЯ
Для каждой значимой стабильной версии желательно иметь:
- README с инструкцией восстановления;
- PDF с итогами теста;
- PowerPoint с итогами теста.

В перспективе документацию лучше хранить в отдельной папке:
DOCUMENTATION/

11. СЕКРЕТНЫЕ ФАЙЛЫ
Никогда не загружать в публичный GitHub:
- config.txt;
- samruk_chrome_profile/;
- Supabase service role key;
- пароли;
- ЭЦП;
- токены авторизации.

12. РАБОТА С НЕСКОЛЬКИХ КОМПЬЮТЕРОВ
Менеджеры работают через браузер и общую Supabase.
Секретный config.txt нужен только компьютеру/серверу-коллектору.

В будущем collector/backend следует вынести на центральный сервер
или выделенный офисный компьютер.

13. КАК БЫСТРО ПОНЯТЬ, ЧТО СЕЙЧАС АКТУАЛЬНО
Сначала открыть:
README_TEST10J.txt

Затем открыть этот файл:
README_VERSIONING.txt

После этого выбрать последнюю стабильную ветку GitHub.

14. ТЕКУЩАЯ ТОЧКА ПРОДОЛЖЕНИЯ
Следующий организационный шаг:
создать ветку test10j-stable.

После этого:
начать новую разработку как TEST10K,
не изменяя стабильную точку TEST10J.
